# v1.0.8 发布后兼容修复设计

## 目标

修复 v1.0.8 自检发现的两项兼容问题，同时保持版本号为 `1.0.8`：

- 玩家佩戴 Enigmatic Legacy 附魔师珍珠时，机械渡鸦附魔台即使没有青金石，也应把三个手动附魔选项显示为可用；实际附魔仍只免除青金石，不生成物品，也不改变经验消耗。
- 玩家曾安装 Easy Magic 并把物品留在附魔台持久化槽位后，即使随后移除 Easy Magic，这些物品也必须能在首次打开附魔台时安全取回。

## 兼容边界

- Enigmatic Legacy 与 Easy Magic 均为可选兼容，不新增编译或运行依赖。
- 未安装对应模组时，不直接引用其类；现有反射与 `ModList` 检查继续作为兼容入口。
- 附魔师珍珠只影响玩家手动附魔的青金石条件与显示，不影响机械自动附魔。
- Easy Magic 未安装时，不继续提供持久化输入、刷新或独立催化剂槽位；迁移只用于归还历史数据。
- 不改变 Apotheosis 的永恒、量子化、阿卡那、宝藏、线索、黑名单、经验、随机种子和事件流程。

## 机械渡鸦珍珠状态显示

`MechanicalRavenEnchantMenu` 当前覆盖 `getGoldCount()`，直接返回机械燃料库存数量。该覆盖绕过 Enigmatic Legacy 对原版菜单的珍珠处理，所以界面会把零青金石的选项显示为不可用，尽管服务器端虚拟燃料逻辑已经允许点击附魔。

修复方式是在该覆盖的最前面调用现有的 `EnigmaticLegacyCompat.isEnchanterPearlActive(player)`。珍珠生效时返回虚拟显示数量 `64`；否则完整保留当前机械燃料计数与客户端缓存逻辑。这个数值只供菜单判定和界面渲染使用，不写入燃料槽，不生成或扣除青金石。

## Easy Magic 历史库存迁移

Apotheosis 附魔方块实体继续读取现有的 `artifice_easy_magic_inventory` NBT，因为删除读取逻辑会让旧存档物品永久不可访问。服务端构造普通 Apotheosis 菜单时按以下顺序处理：

1. 如果 Easy Magic 已加载，继续绑定三格持久化库存，行为不变。
2. 如果 Easy Magic 未加载且持久化库存非空，执行一次迁移。
3. 输入槽物品优先迁移到普通附魔输入槽；燃料槽物品优先迁移到普通燃料槽。
4. 若对应普通槽已经被占用，则不覆盖现有物品，而是把待迁移物品归还玩家物品栏；物品栏放不下时沿用 Minecraft 的玩家归还逻辑掉落剩余物，避免丢失。
5. Easy Magic 独立刷新催化剂没有普通目标槽，直接归还玩家物品栏。
6. 每个源槽只有在目标槽接收或玩家归还调用完成后才清空，防止复制或丢失；方块实体随后标记为已更改，使清空结果写回存档。

迁移在服务端执行，客户端不处理持久化物品。迁移完成后，普通附魔台、渡鸦附魔台和机械渡鸦继续使用各自原有的非 Easy Magic 菜单行为。机械渡鸦的旧 `savedEnchantSlot` 恢复逻辑不得覆盖刚迁移的输入物品：仅在普通输入槽为空时恢复旧槽，否则将旧槽物品归还玩家并清空旧保存值。

## 数据安全与异常处理

- 空源槽不做任何操作。
- 普通目标槽为空时整栈移动，源槽清空。
- 普通目标槽非空时不尝试合并不同语义的附魔输入；整栈归还玩家。
- 玩家归还使用游戏已有的 `placeItemBackInInventory` 路径处理满背包情况。
- 迁移仅由服务端菜单构造触发，并在源库存真正发生变化时调用方块实体 `setChanged()`。
- 已清空的持久化槽位在以后打开时不会再次迁移。

## 测试与验证

采用测试驱动方式逐项实现：

- 先添加机械渡鸦珍珠显示回归测试，要求 `getGoldCount()` 在读取真实燃料前检查珍珠，并确认旧实现下失败。
- 再添加 Easy Magic 移除迁移回归测试，覆盖输入、燃料、独立催化剂、目标槽占用、源槽清空、服务端限定和机械旧保存槽不覆盖，并确认旧实现下失败。
- 实现后运行定向测试、全部单元测试、`git diff --check`，并使用 Java 17 执行完整 `clean build`。
- 检查产物元数据，确认 Easy Magic 与 Enigmatic Legacy 未成为强制依赖。
- 将正式 JAR 输出到 `C:\Users\Lenovo\Desktop\Ai_Run\output\apotheosis_artifice-1.0.8.jar`，不部署到 `mods`。
- 游戏内重点验证：零青金石佩戴珍珠时机械渡鸦选项显示可用且手动附魔不消耗青金石；移除 Easy Magic 后首次打开三类附魔台能取回历史槽位中的所有物品。

## 发布

验证通过后保持 `mod_version=1.0.8`，将修复提交合并到 `master`，强制更新现有 `v1.0.8` 标签到新提交，覆盖同名 Release JAR，并更新 Release 说明。最终核对远端 `master`、`v1.0.8` 标签、Release 目标提交和本地构建提交一致，并报告新的 SHA-256。
